## Approved local dispositions and measured preservation

- **SEC-01:** Replace proxy-socket source buckets with a service entry ceiling of 120/minute and 600/hour, and challenge attempts of 6/minute and 30/hour for each validated run. A blocked run no longer consumes a neighboring run's small allowance; global rotation/capacity/paid ceilings remain. No forwarding-header trust or visitor tracking. Exact batch child minting still needs no additional challenge. Reset retains run attempt state. Tests cover neighboring runs and expired global windows.
- **SEC-02:** A shared complete-binding validator now runs after bounded parsing/actual bytes/hash and before operation tracking, workspace reservation or inspection. Atomic consumption reuses that validator after awaits. Wrong workspace/operation/input/hash/retry/cookie calls create zero tracked operations/reservations/workers/provider starts; the same token's genuine request remains usable. Matching concurrent replay has one provider start. No extra failed-inspection claim is needed: once full binding prevents identity substitution, the existing operation reservation rejects repeated matching inspection attempts.
- **SEC-03 (application-only):** One frontend guard implementation supplies 120/minute read and mutation windows plus four large-operation leases. Pages/image work use the proxy's own window; API guards run in the server handlers, before body reads, so Next's automatic proxy body buffering is avoided. Scope is each serving runtime/module, not a durable service/visitor quota or volumetric DDoS guarantee. Malformed cookie/grant values reject before config; missing live headers reject before body acquisition. A first backend capability read can be necessary to establish authoritative fake/live mode; it is coalesced only while in flight, with no stale availability cache. Aborted callers release immediately without canceling other cold-start waiters. FX misses coalesce, orphaned work aborts, and failed lookups back off five seconds without a stale/fabricated rate. No infrastructure change.
- **SEC-04:** In an isolated 1 CPU/1 GiB, read-only, network-disabled Linux candidate, four 797,346-byte synthetic inline-image PDFs (7,000 images / 68,607,000 pixels each) reached **989,671,424-byte process RSS / 945,635,328-byte cgroup peak**, with four 20-second timeouts. This demonstrated inadequate headroom, not a hosted OOM or RCE. The selected repair permits **two native inspections and two bounded foreground waiters**, retaining four upload/provider requests. Waiting shares the 20-second deadline; a **640 MiB process RSS stop sampled every 10 ms** terminates inspections, and settlement/lease release awaits actual worker termination. The identical pressure case then rejected safely at **671,436,800-byte RSS / 623,337,472-byte cgroup peak**. All ten originals/eighteen pages still inspected; four 5 MiB/five-page synthetic copies (20 MiB/20 pages) succeeded at 255,070,208-byte RSS. Four cancellations released active/waiting work and a subsequent D01 succeeded. The RSS check is a measured safety margin, **not an OS-enforced allocation ceiling**; pathological instantaneous allocation and native-library uncertainty remain residual risks, without claiming arbitrary-PDF certification. No helper service, instance resize or reduction of paid/provider slots.

## Assets, data flow and trust boundaries

1. **Guest browser → public Next service.** Inputs are attacker-controlled: headers, cookies, grant strings, workspace/projection JSON, chat text, multipart metadata and PDFs. Browser-local records are the visitor's editable data, not proof of authentic accounting records. There is no shared account database or transfer/payment authority to obtain by editing one's own tab.
2. **Public Next → private Express service.** Only fixed configured paths/targets are forwarded. The server obtains its own Cloud Run identity token; browser Authorization/Host/forwarded headers do not supply backend authority. Cloud Run enforces invoker IAM. Origin/CSRF policy is separately checked by both apps.
3. **Express → PDF worker.** Bytes are untrusted native-parser input. Intake bounds, hash/length checks, feature rejection, worker termination and deadlines constrain work. A worker thread shares process memory and OS identity; it is not a separate security principal or an OS sandbox. SEC-02 and SEC-04 concern this boundary.
4. **Express → OpenAI / Turnstile / fixed FX provider.** Only application-owned endpoints are used; redirects are rejected. Transcription receives PDF bytes and supplied context. Retro receives recent conversation/validated current records and bounded context, not the original PDF attachment. Turnstile gets its opaque token/action/hash. FX sends no visitor records. Secrets stay backend-only; the public site key is intentionally public.
5. **Generated output → browser actions.** Provider output is untrusted, runtime-validated structured data. Exact fact IDs, tool arguments and deterministic money results ground it. Model changes become editable proposals requiring visitor confirmation, current revision validation and the normal command engine. The model cannot execute code, call arbitrary HTTP, write storage or authorize a financial/layout command on its own.
6. **Repository/build → deployed image/runtime/logs.** Frozen lockfile, build-script allowlist/release-age policy, positive Docker context, digest pins, nonroot images and private runtime secret access protect the release. Logs are content-free private operations; browser errors use owned guidance/generic fallback. No uploaded-file library, document bucket, hosted database, persistent chat store or background queue exists.

Assets to protect: visitor documents/records/conversation; signing/provider secrets and service identity; exact calculation/source integrity; deliberate action consent/replay prevention; the demo's availability; bounded provider/cloud cost; private diagnostic continuity. A demo need not acquire user accounts or persistent storage merely to apply these controls.

## SEC-01 — Shared pre-challenge admission allowance can block other visitors

**Severity:** Medium. **STRIDE:** Denial of service; visitor-identity misclassification. **Confidence:** High for control flow and local effect; medium for the number of hosted visitors sharing each ingress socket address. **Affected asset:** starting a live session and issuing verified batch/chat grants.

### Evidence and attack path

- `apps/backend/src/security/routes.ts:100` derives the source key from `request.socket.remoteAddress`. `routes.ts:103` counts a new-cookie session attempt before any challenge. Grant/batch issuance calls the same `attempt` before verification (`security/admission.ts:179`, `:230`). Express explicitly disables `trust proxy`.
- `security/admission.ts:111` limits each source to six attempts in a minute and thirty in an hour. It uses an HMAC of the immediate network peer, not an authenticated visitor.
- Local paid-config/synthetic-verifier observation made seven well-formed new-session requests without a cookie: **200, 200, 200, 200, 200, 200, 429**. There were **zero provider calls and zero verifier calls**. Advancing a fake clock through five permitted minute windows filled thirty attempts and blocked the hour.

An unauthenticated client can submit new sessions or failed grant requests repeatedly. Visitors routed through the same backend peer then lose the same small allowance. The frontend/Google proxy is the backend's network peer, so the bucket cannot be assumed to represent an end user. The precise hosted peer pool and duration of grouping have not been measured; this is not a claim that every visitor always shares one address.

### Impact and existing defenses

The cheap admission guard works as written, cannot be bypassed using arbitrary X-Forwarded-For, and prevents unbounded challenge calls for one peer. It also penalizes innocent neighboring visitors. Users may see generic inability to begin/continue processing even though they have not exhausted their own run allowance. No money change, document exposure or unauthorized provider call was demonstrated.

### Original repair plan — subsequently approved

1. Give the existing service-wide protection and individual run protection distinct ownership/names. Do not describe a proxy-peer bucket as a per-visitor control. Keep a bounded global pre-challenge request/capacity guard sized against legitimate ten-document/four-turn activity and simultaneous visitors, rather than silently deleting rate protection.
2. After a valid run/challenge exists, apply the small action allowance to the validated run identity, preserving the global 20/hour paid-start ceiling and four active paid operations. A fresh cookie is not proof of a new person; keep global ceilings to constrain run rotation.
3. Apply a cheap frontend pre-challenge guard as part of SEC-03. If visitor-IP fairness is required, choose an ingress that provides a documented trustworthy identity and seals bypass first. Only then forward a narrow application-owned identity assertion that the private backend verifies. Never turn on blanket proxy trust or accept an attacker-supplied forwarding header.
4. Keep all operational events; report curated retry/availability guidance to visitors. Any added denial reason must be a fixed content-free field in private metrics, never an IP, token, body or source record. No hosted user database or persistent person-tracking service is proposed.

**Candidate files:** `security/admission.ts`, `security/routes.ts`, their tests, shared admission constants only if an approved policy needs them; frontend admission/bridge guard and tests shared with SEC-03; security-admission engineering/ticket/evidence documents. Cloud ingress templates/runbook only for an explicitly selected edge option.

**Preservation checks:** a single batch still obtains ten exact child grants after one challenge; no new processing dialog; valid visitors on the same peer can complete the authorized normal workflow; one abusive run cannot reset its own counters; malformed/forged forwarding headers confer no authority; failed challenges cannot mint grants; global ceiling, four parallel slots, expiry/reset/boot and paid-off behavior remain. Use a fake clock and two distinct valid runs sharing a peer. Hosted identity/fairness testing needs separate approval and bounded, content-free observation.

**Rollback / decision:** an application change should be independently reversible with no storage migration. Owner must decide whether demo-sized shared/run guards suffice or verified edge visitor fairness is required. Accepting current behavior means accepting avoidable shared lockout. The dated audit made no policy change; the later approved policy is recorded above.

## SEC-02 — Complete upload grant binding occurs after workspace and PDF work

**Severity:** Medium. **STRIDE:** Tampering and denial of service. **Confidence:** High. **Prerequisite:** the attacker first obtains one legitimately verified, unexpired extraction grant and its run cookie. **Affected assets:** native inspection capacity and process-local extraction bookkeeping.

### Evidence and attack path

`documents/extract-route.ts` runs paid preflight before multipart intake. That correctly rejects absent, forged, expired or consumed tokens. However, `PaidAdmission.preflight` (`security/admission.ts:341`) checks the run/token/action, not the supplied request's complete identity. After parsing, the route tracks `metadata.workspaceId` (`:53`), reserves extraction counters (`:55`) and runs `inspectPdf` (`:61`). Only then does `consume` (`:72`) verify workspace/operation/input hash/document hash/retry and reserve paid cost atomically.

The bounded local observation reused one valid grant with two different, validly shaped metadata workspace/operation values and the real D01 bytes. Both requests returned **403 `invalid_grant`**, and **zero provider calls** occurred. The injected extraction-reservation observation recorded both unapproved workspace IDs; the original token still passed preflight afterward. Source order shows inspection ran before the eventual binding failure. This reproduces unnecessary work/side effects, not a paid authorization bypass.

Until expiry, the same valid token can be submitted with mismatched metadata and fresh operation/workspace IDs. It can occupy parsing slots and add rejected-request bookkeeping without consuming that grant. Counters are bounded to 1,000 workspaces/four active operations, so memory is not unbounded, but this can deny useful capacity. An attacker does not obtain another visitor's documents by guessing a workspace ID.

### Original repair plan — subsequently approved

1. Add a **side-effect-free complete binding check** in the ledger, reusing the same identity validation as paid consumption. Avoid two separately maintained comparisons. It must check cookie/run/epoch/expiry/nonce/action and exact metadata-derived identity, including input hash, document hash and retry.
2. After bounded multipart/schema parsing and actual byte/hash verification, run that complete check **before** operation tracking, workspace counters and `inspectPdf`. Unapproved input must not create a workspace budget or native worker. Multipart parsing cannot entirely disappear before metadata is available; retain its existing byte/capacity limits.
3. Keep the final atomic consume/reservation immediately before provider dispatch, with a fresh validation after awaits. Do not consume or charge the grant before proving a PDF is supported; doing so would break legitimate held-file behavior and burn allowances on unsupported originals.
4. A fully matching grant can still be retried with an unsupported PDF until expiry. If the approved design requires stronger protection here, use a small request-local inspection claim tied to the grant nonce and bounded failure attempts, released on abort/completion. Document this as an explicit policy choice; do not refund an unknown provider outcome or add automatic retries. SEC-03 remains the general flood guard.

**Candidate files:** `security/admission.ts` and tests; `documents/extract-route.ts`; HTTP/extraction regressions in `http/app.test.ts` or existing root extraction tests; admission documentation/validation. Do not change provider prompts, amounts, source-order commits or browser money ownership.

**Required negative tests:** wrong workspace, operation, input/document hash, retry, action, expired/consumed nonce and duplicate cookie create no operation tracking, extraction budget or worker and dispatch nothing. Race two matching requests; at most one provider start. Reset/revoke while inspecting must fail closed before dispatch and release resources. Unknown paid outcomes retain the full reservation.

**Required positive tests:** genuine ten-PDF batch, four overlapping requests, supported byte/hash/page checks, held unsupported source guidance, explicit single retry, existing originals/source drill-down, canceled intake, latest Undo and fake mode all remain. A rejected mismatched request must not prevent the original approved request from succeeding. No new UI consent step or raw technical message.

**Rollback / decision:** this is a cohesive ledger/route change with no new service or storage. Owner decides whether to fix the demonstrated ordering gap and whether additional failed-inspection policy is in scope. The ordering repair is now implemented locally; existing operation reservation supplies repeated-inspection protection after full binding.

## SEC-03 — Public requests can consume runtime capacity before paid gates

**Severity:** Medium. **STRIDE:** Denial of service and resource/cost abuse. **Confidence:** High for routes/configuration; medium for realistic outage duration and cost. **Prerequisite:** none for public GETs; an automated client can supply the canonical Origin for POSTs. **Affected assets:** frontend responsiveness, private backend free-route capacity and legitimate processing availability.

### Evidence and attack path

- The deployed frontend is publicly invokable with ingress `all`; the managed URL remains reachable. The owner configured Cloudflare DNS-only apex records, which add no Cloudflare request filtering. Turnstile authorizes paid actions, not every request to the website.
- `/demo` is rendered with per-request nonce security headers; config/FX API handlers remain public. `server/capabilities.server.ts:12` obtains private runtime config with a ten-second deadline on every call. `backend.server.ts` obtains metadata identity and forwards fixed authenticated requests. This is correct authority separation, but public traffic can drive that work.
- `server/extraction.server.ts:29` reads capabilities before any cookie/grant check, then streams up to **5 MiB plus multipart overhead** to the backend; backend preflight rejects an absent grant before native inspection. `server/retro.server.ts:25` reads capabilities and `:32` parses up to **2 MiB** before building/validating admission headers and forwarding. The frontend has no shared application request-rate guard.
- FX caches a successful dated quote for one hour, but `providers/exchange-rates.ts` has no in-flight coalescing or short failed-lookup backoff. Concurrent cold requests or an upstream outage can create repeated fixed-provider calls. No visitor data is sent.
- Frontend concurrency is eight, backend six; existing body deadlines are bounded but can occupy slots for tens of seconds. Four expensive intake slots and short header timeouts protect backend work. Cloud Run itself handles lower-level infrastructure traffic; no hosted volumetric attack was tested.

An automated client need not solve a challenge to render pages, poll free APIs or submit well-shaped but unauthorized bodies. It can compete with real visitors for small-instance CPU/concurrency. The existing USD 5 Cloud Run cap helps bound gross runtime spending with documented lag, but pausing at the cap can itself stop the demo. It does not identify abusive requests or keep the app responsive.

### Original repair plan — subsequently approved

1. Start with one small **shared frontend admission component**, not separate ad hoc limits in every handler. Bound both public cheap requests and active streamed/large requests; reject cheaply with curated 429/503 responses. Choose thresholds against a recorded legitimate sample batch, navigation/config/FX startup, mobile use and four concurrent uploads. Reserve reasonable capacity for ordinary page/config access without creating per-person tracking.
2. For paid routes, reject absent/duplicate/malformed cookie/grant headers before capabilities calls or reading a large body. This is a syntactic filter; only the backend can establish authenticity. Preserve fake-mode behavior and avoid requiring paid cookies for anonymous FX/config/landing or deliberate session creation. Server-to-backend origin/IAM checks stay intact.
3. Coalesce concurrent fixed FX misses and, if needed, capabilities reads within a short bounded process-owned window. Each caller must retain its abort ownership; one aborted visitor must not cancel everyone else's lookup. A brief failed-lookup backoff must never invent a rate or return an expired quote. Capability caching must have a documented short freshness ceiling and may not reopen paid-off state, recreate the prior cold-start defect or cache token/visitor data.
4. Decide whether the expected sharing scale warrants an edge protection service. Application guards mitigate request work; they are not a guarantee against a large network flood. If selected, a Google external HTTPS load balancer/Cloud Armor path with appropriately restricted frontend ingress can seal the managed-URL bypass. [Cloud Run ingress documentation](https://docs.cloud.google.com/run/docs/securing/ingress) describes `internal-and-cloud-load-balancing` for this path. This is an optional owner infrastructure choice, not an automatic requirement for a demo.

## SEC-04 — Worker heap limits do not bound complete PDF memory use

**Severity:** Medium, as an unresolved material availability risk. **STRIDE:** Denial of service. **Confidence:** High for the control gap; medium for maximum allowed-PDF resident memory/hosted failure. **Prerequisite:** an approved extraction request carrying a demanding PDF. **No malicious-PDF OOM or code-execution exploit was attempted or demonstrated.**

### Evidence and realistic impact

`documents/inspection.ts:24` bounds old/young JavaScript heaps to 128/32 MiB and stack to 4 MiB. It also terminates the worker at twenty seconds and on abort. These are useful controls. Node's [worker documentation for the pinned runtime](https://nodejs.org/download/release/v24.19.0/docs/api/worker_threads.html) says these heap limits exclude external data such as ArrayBuffers, and whole-process memory exhaustion can still abort the process.

The local bounded demonstration configured an **8 MiB old-generation** worker and successfully allocated a **32 MiB ArrayBuffer**; reported external memory was approximately 35 MiB. This proves the limit's scope, not a PDF exploit. The demo worker was terminated afterward.

`documents/inspect-worker.mjs:45` materializes `getOperatorList()` before checking 100,000 operators or the aggregate 80-million-pixel limit. Per-image `maxImageSize` is twelve million pixels, but decoded images/native buffers, raw/byte copies and PDF.js allocations are not all accounted by V8 heap limits. The loop only totals selected paint operators after list creation, so that aggregate is not a proven pre-allocation ceiling. Four inspection requests can share the backend's **1 GiB** container. A small compressed file can require far more memory when decoded; a 5 MiB file limit is not a decoded-memory limit.

Page/file/body/deadline limits, unsafe-feature rejection and four active intake slots prevent unbounded normal work. They do not prove that every allowed four-PDF combination fits in the deployed memory. Shared OOM could interrupt innocent requests and restart the in-memory run ledger, requiring deliberate recovery. Other tabs' private files are not thereby disclosed.

### Original measurement-first plan — subsequently approved

1. Reproduce the **actual Linux 1 GiB envelope** in an isolated local candidate, with fake/no-key composition. Measure process/container peak RSS and external memory for all ten originals, four simultaneous maximum-envelope supported files and carefully bounded synthetic compressed/image/operator-heavy inputs. Cap time/memory at the test container and stop after the stated workload; never run this against production. Record cancellation/cleanup and fifth-request rejection. Do not expand to an unbounded fuzzer or upload private documents.
2. If peaks stay safely bounded, document the observed margin and decide whether to accept the residual parser limitation. Measurement does not establish safety for every possible PDF; keep the limits and monitor content-free operational outcomes.
3. If a bad case is demonstrated, first cover actual decoder/operator paths earlier where the pinned PDF.js API supports it, including grouped image operators. Do not apply a byte-to-pixel heuristic that rejects normal scans or handwritten bills. A post-decode count must not be advertised as prevention of pre-decode allocation.
4. If early limits cannot reliably isolate the allocation, choose the smallest proven containment: an inspection-specific concurrency/memory lease or a request-local helper process with an enforceable memory limit. A helper is a request-owned implementation detail, not a new background queue/service. Do not globally lower all four paid/provider slots by default; preserve overlap where safe and document any user-visible throughput tradeoff before choosing it.
5. Keep all existing private operational events and parser payload privacy. Fail with existing curated unsupported/busy guidance; no raw decoder stderr, lost completed sources, automatic retry or permanent document storage. Preserve termination on abort/reset/expiry and clean up every worker/helper/lease.

**Candidate files only if evidence warrants a fix:** `documents/inspection.ts`, `inspect-worker.mjs`, a small request-local inspection-capacity/helper module if necessary, extraction route integration and meaningful parser/cancellation regressions; Docker/runtime template only if the owner selects a changed memory envelope; ticket/operations/evidence. The initial audit did not select a new process, inspection limit or larger instance. The later measured inspection-only remedy is recorded above; paid/provider concurrency and instance size are retained.

**Preservation checks:** the ten originals still process with the same holds/exact outputs; scans, handwriting, two-page originals, source drill-down and byte-identical downloads still work; 5 MiB/file, 20 MiB/ten-source batch and twenty-page limits remain as documented; four-request normal overlap/source-order commits and fifth-slot rejection; abort releases memory and permits later work; completed records survive failures; browser motion and no-new-dialog behavior unchanged. Host billing/performance changes need explicit rollout approval.

**Owner decision:** approve the bounded measurement first, accept the documented gap, or defer. Only measured results can select the eventual fix; this audit does not pretend to have completed RET-012's pending peak-memory acceptance.
