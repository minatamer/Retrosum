## Admission and reservations

**Latest owner four-document implementation:** One production Turnstile verification approves a canonical manifest of at most ten distinct exact PDF request identities. A fixed ten-minute content-free batch approval cannot dispatch extraction directly; fresh two-minute, single-use grants are minted just before each approved upload. Changes to operation, input hash, PDF hash, retry, workspace or run reject. Reset/expiry/boot change invalidate approval; no token is reused at Siteverify and no future selection is authorized. Four browser workers overlap bounded requests, with selection-order commits against the latest batch-owned revision. Cancel aborts all active slots, preserves completed sources and leaves queued originals unsubmitted. The accepted model, prompt, exact token preflight, standard tier, twenty/hour paid starts, ten originals/one retry and USD 2.50 conservative reservation remain unchanged. The initial session uses the global service entry window; batch/Retro challenge verification also uses the validated run's six/minute and thirty/hour window. Bounded just-in-time minting uses the approved manifest without further challenge attempts.

The backend ledger holds no financial content: workspace/run identity, hashes, operation/nonces, times and aggregate reservations only. HMAC grants bind the boot epoch, run, workspace, action, operation ID, parsed-input SHA-256 and, for extraction, original SHA-256/retry identity. Cookie claims use the same epoch/run/deadline. Invalid signatures, duplicate cookies, wrong inputs/classes/workspaces, expiry, prior boots and replay reject. Header preflight runs before large JSON or multipart parsing. Full extraction binding is checked after bounded original validation, before tracking/reservation/inspection, then again at atomic dispatch.

Consumption is synchronous: allowance checks, full maximum cost reservation, consumed-operation state and an independent lease within the four-slot instance limit happen without an intervening await. Releases are idempotent and cannot free another operation's lease. Unknown outcomes retain the full reservation. There is no refund based on a lost response, automatic SDK retry or durable replay cache. Reset discards unused grants and batch approvals and cancels owned controllers; it preserves the independent run cookie, consumed identities and reservations. Refresh does not renew the run deadline. A new workspace cannot reuse the old cookie’s allowance.

A correctly signed cookie from a previous server boot rejects the session action with 409 and expires only that obsolete cookie. The bridge forwards only the exact secure deletion for `boot_changed`; a new action must be deliberately submitted and challenged again. Valid current cookies, wrong workspaces, invalid signatures, expiry and spent allowances are never cleared by this recovery. This permits local restart recovery without automatic action resubmission or current-run allowance renewal.

## Diagnostics and privacy wording

Backend output includes only the allow-listed route, capability mode, HTTP status and bounded rounded duration. It excludes documents, extraction text, chat/contact fields, filenames, source IP, secrets, cookies, grants, arbitrary IDs and raw error objects. A diagnostic sink failure cannot break a request. Usage returned to a requesting client is not printed as a payload. Detailed provider usage and billing measurement remain owner-run evidence, not invented telemetry.

Application request memory is transient; no server originals, Files API library, bucket, database or hosted conversation store is added. `store:false` does not establish universal zero retention. Default API abuse monitoring can retain content for up to thirty days, with file/image and account-policy exceptions. The product links the actual policy rather than promising instantaneous deletion. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data).

RET-012 established owner-approved **seven-day** default operational log retention. Required audit retention was unchanged. RET-013 retains every existing application operational event and does not change retention or cloud resources. Reset clears browser-owned data, attempts remote cancellation and preserves allowance state. It cannot retract prior downloads or provider-controlled retention.
